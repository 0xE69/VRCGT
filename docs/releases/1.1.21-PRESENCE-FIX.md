# 1.1.21 — final multiline-log security repair (fix cycle 2)

## Architecture and coverage

The first envelope-only repair was insufficient: splitting on LF loses message provenance, and arbitrary Udon continuation text can reproduce a bare or timestamped player record. Adding another regex cannot establish identity/presence. The parser is retained only as a local discovery/departure hint; no automatic authorization relies solely on it.

Automatic eligibility now requires a separate read-only `GET users/{userId}` through the existing authorized client. The response must explicitly contain the exact `id`, `state=online`, and full `location` equal to the confirmed world plus instance, with no travel destination. No missing-ID fallback, count, bio/status/profile claim, destination-only travel field or previous log record is accepted. A separate method/DTO isolates this strict policy from existing manual/profile metadata consumers. The acting-account/auth-generation repair in CurrentInstanceInviteWorkflow is untouched.

**Limited automatic coverage, not all occupants:** User.location is optional and privacy/friend-limited. Hidden/private/offline/non-friend/unknown/error/expired evidence is skipped, never automatically retried for an unchanged candidate during that confirmed session. The UI confirmation, persistent explanatory text, row pending/unknown state and AUTO-INVITE.md say so. Manual explicit selection/review is preserved. For all-occupant coverage, the parent must discuss a different trusted architecture with the user; do not publish this as universal coverage. A creator-only instance roster is documented, but not silently implemented as a universal source.

One preparation runs at a time while five-second local polling continues. Membership/history/filters are checked first. New-candidate presence reads are at least 13 seconds apart, independently of the existing 13-second send pacing. A ten-second timeout bounds each read; positive evidence expires 20 seconds after lookup start, including API pacing and transport time. The final central pre-HTTP guard rechecks exact context/auth generation, local departure and bounded evidence freshness after pacing. Expiration fails closed; it does not trigger a new read on every poll/send. Explicitly starting a new confirmed session creates a new evidence cache.

This corroborates an API-visible presence snapshot, not a cryptographic guarantee of physical attendance or zero server propagation delay. No API freshness guarantee or universal roster is invented.
