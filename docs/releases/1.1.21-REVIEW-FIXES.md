## Untrusted player-event log text

Root cause: occupant discovery searched anywhere in a line for `OnPlayerJoined` or `OnPlayerLeft`, accepting Udon and unrelated messages as authoritative presence.

Fix: anchor the recognized envelope: optional `yyyy.MM.dd HH:mm:ss Log -` prefix, then `[Behaviour]` and the player event itself. Bare `[Behaviour]` events used by existing fixtures remain supported. Udon/unrelated loggers, nested logger strings and embedded event tokens are rejected. Timestamped/bare joins and departures and unresolved name-only rows are preserved. No private locations were added to logging.

`tests/AutoInviteTests/UntrustedLogTests.cs` runs six negative envelopes after a legitimate completed join, using the real compiled viewmodel discovery, eligibility and final-presence guard; real AutoGroupInviteSession; and real central API/ledger boundary with an outer HTTP-deny handler.

- **RED before production edit:** `vrcgt-auto-red.log`: **29/35 passed**; all six negatives failed with **occupants=1, eligible=1, HTTP=1**. The deny handler blocked actual transport.
- **GREEN:** all six now assert **occupants=0, eligible=0, HTTP=0**. This is not merely a parser-unit pass. A positive control also checks recognized timestamped/bare events and confirms untrusted Left messages cannot remove real occupants. Existing compiled WPF opt-in integration still sends successfully through a fake HTTP handler.

## Acting account/authentication generation

Root cause: current-instance workflow pinned only destination, allowing changed acting authentication to inherit earlier consent.

Fix: production factory supplies `(CurrentUserId, InvitationSession)`. Snapshot before confirmation, reject absent authentication, require unchanged identity/generation for each recipient after batch pacing, and recheck after actual API pacing immediately before HTTP. Changes stop remaining recipients as NotSent, retaining already-completed outcomes. A later deliberately confirmed batch obtains a fresh snapshot.

`tests/InstanceInviteTests/AccountPinTests.cs` uses real VRChatApiService auth state and HTTP-deny handlers for same-account logout/relogin and different-account changes, both during confirmation and actual API pacing.

- **RED before production edit:** `vrcgt-account-red.log`: **25 passed, 4 failed**. Each case reached **HTTP=2**; the deny handler caused Unknown outcomes instead of reaching any real endpoint.
- **GREEN:** all four cases assert **HTTP=0**, every recipient NotSent. Additional tests independently change only account ID with generation unchanged, and change auth generation during inter-recipient pacing (prior Sent retained, remaining NotSent). Existing destination/cancellation/transport outcome and compiled Friend Manager/DI checks remain green.

Two harness issues were corrected before capturing the final RED: synthetic process-start time must remain stable between reads; the API limiter stores local `DateTime.Now`, not UTC. The initial UTC pacing probe timed out; the final recorded RED/GREEN runs use the actual limiter's clock convention. No production workaround was introduced.
