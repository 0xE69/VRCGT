# 1.1.23 — history GROUP invitations

## Corrected semantics

GROUP invitations target membership, not a destination instance. Manual Game History selection and opt-in Auto support current AND previously encountered users after room changes, room ending/disconnect and VRChat client closure. CurrentInstance/SessionKey/world ownership/process/API presence or visibility are not group eligibility requirements; JoinNotObserved is informational. Friend-to-instance destination/account-authentication guards and live announcement privacy/publication approvals are unchanged.

## Integrated scope

- Game Log loads retained history and has explicit bounded Scan imports (at most ten files, <=20 MiB per file; no new header guesses). Up to 1,000 encounter identity/source records persist in the existing local SQLite database. Ordinary load/refresh/select-all never enables automation or sends.
- Records are untrusted, user/world-controlled discovery, NOT verified live presence, authenticated provenance or proof of encounter. Fabricated text can contain a real UUID. Recipient selection/history-scope consent is the authorisation boundary. Display names do not authorise a first-match target; malformed IDs, unresolved/ambiguous names, self and known members/blocked identities skip.
- Manual Game Log selects eligible visible records only and confirms exact group/account/recipients. Acting account and authentication generation are pinned before confirmation and checked again after pacing at HTTP dispatch.
- Instance Inviter navigation is preserved but clearly labels Auto GROUP invitations. Enabling confirms exact account/group, visible current/past exact-ID snapshot/count/filters and whether future exact-ID LOCAL tracking records are included. That source/scope is explicit in the confirmation. Future raw imports and contacts never silently broaden consent. With future scope off, newly discovered records need review/reconfirmation; with it on, future tracked exact IDs are consented discovery and may be fabricated, as warned.
- Queue polling is five seconds, with no overlapping preparation/sends. Group sends remain >=13 seconds apart plus central API pacing/Retry-After. Off/logout/acting-account/auth-generation/group/filter/history-scope changes, view close or app close revoke consent; room/client changes do not. Restart is always disabled.
- Strict identity uses a separate API adapter, not the legacy profile DTO fallback. The actual response must contain the exact matching string `id`; filters off is not a bypass. Identity and error results are reused only within the same acting-account/auth-generation/selected-group scope. The final central dispatch guard requires that evidence after pacing. Optional presence/location/state/world fields are never read as identity requirements.
- Future local discovery uses an independent read-only incremental reader of the default VRChat output-log directory: at most the latest 16 files, last 5 MB/file, 1 MB/check, complete records <=16 KiB and a shared retained bound of 1,000 IDs. It reads Joined records even without a completed join or running process; Left/disconnect/room-ended records do not delete history. Explicit imports stay outside future scope. Unknown headers are classified unsupported rather than silently promised readable.
- Known membership cache evidence is used first. Unknown candidates can use bounded paced exact reads, cached even on error. Only a successful `200 null` proves nonmembership. 404/403/429/network errors/malformed responses stay APIError/Unknown, never assumed nonmember. Explicit Game Log membership review is at most twenty visible unknown/error targets per click. Enabling does not require a complete whole-group cache.
- All group entrypoints keep the shared atomic exact-group/recipient ledger before HTTP. Sent/InFlight/Unknown suppress duplicates across restarts/features. Failed requires deliberate manual retry; no uncertain automatic retry. Cancellation after dispatch can be Unknown. Completion storage failure keeps the durable blocking claim.

## Limits / acceptance

Known-format exact-ID local Joined records are required to DISCOVER new users; this is not live-presence evidence. A Joined/Left pair between polls is retained. Unsupported headers, records outside the bounded scan/file range, missing IDs, inaccessible logs, unknown identity/membership or API errors can remain unavailable/pending. Existing explicit Game Log scanning/manual selection after client closure remains available. There is no all-contacts, unbounded archive scan or omniscient encounter-capture claim. Initial parser scans can pause UI. The published 1.1.22 log-header incident remains unconfirmed pending v2 diagnostic user data; this release does not claim a header fix.

Offline fixtures use fake HTTP, disposable SQLite/logs and a plain WPF Application. They do not log in, send live invitations, run production App startup or mutate the real user database. No public upload/tag/commit is performed by this child; frozen local artifacts are for parent review and authorised publication.
